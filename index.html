How I build AI systems

Grounded answers are an engineering property, not a prompting trick. I work in three layers, because a demo is not an eval.

Retrieval is a graph problem

Vector search finds similar text. It does not know that a receipt belongs to an invoice, that an invoice belongs to a filing period, or that two documents describe the same entity. I build a lexical graph (documents, chunks, entities, community summaries) so retrieval can enter at a chunk and traverse to evidence a vector alone would miss.

Depending on the question, that means graph-enhanced vector search, parent-child retrieval for context, or a community summary when the question is about the whole corpus rather than one passage.

The harness is where quality lives

An answer that cannot be reproduced cannot be trusted. Every system I build has a harness around it: query rewriting and entity extraction before retrieval, reranking and pruning after it, structured outputs, and a trace for every step.

I keep a small, hard eval set built from real failures. Each fix becomes a regression test; each release runs against the same cases. Latency and token cost are budgets, not afterthoughts.

It has to ship

Retrieval quality is wasted if the product cannot use it. I build the Go services and APIs around the model: streaming responses, citations the reviewer can open, permissions on every document, and a human review step before anything is filed.

The output is not a chat transcript. It is a case file with evidence, and a reviewer who can see why the system said what it said.

Patterns I reach for

Basic retriever
Vector or full-text entry into the graph.
Graph-enhanced vector search
Vector hits expanded through relationships.
Parent-child retriever
Match small chunks, return the larger passage.
Local retriever
Entity-focused traversal for specific questions.
Global community summary retriever
Corpus-level questions over community summaries.
Dynamic Cypher generation
Structured questions translated into graph queries.
